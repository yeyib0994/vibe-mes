# FluxMES · Spec Kit 约定（conventions）

本文件定义 `specs/` 下所有文档必须遵守的写法约定，供人工编写与（未来的）脚本校验使用。模板见 `.specify/templates/`。

## 1. EARS 需求格式

所有功能需求（spec 的「功能需求」章节）必须采用 EARS（Easy Approach to Requirements Syntax）：

```
[WHEN <触发事件>] [IF <条件>] THE SYSTEM SHALL <可观测行为>
```

- 每条需求以 `FR-<n>` 编号，编号在模块内唯一、稳定（重排勿改号）。
- 条件句式可选；含条件时以 `IF` 引导，触发以 `WHEN` 引导。
- 工业级（原型尚未实现）的需求在句首标注 `（工业级）`。
- 原型已具备的需求在句首标注 `✅`，并在「现状对照」表中复用该标记。
- 行为须可观测、可验证，避免「友好」「高效」等不可测形容词。

非功能需求以 `NFR-<n>` 编号，须带量化阈值（如「< 1.5s」「WCAG 2.1 AA」）。

## 2. 优先级图例

| 级别 | 含义 | 典型落地阶段 |
| --- | --- | --- |
| P0 | 必须，缺它模块不可用 / 不合规 | Phase 1 |
| P1 | 重要，显著提升能力或合规完整度 | Phase 1–2 |
| P2 | 增强，体验/效率优化 | Phase 2+ |

## 3. 命名规范

- **模块 slug**：kebab-case，如 `production-cockpit`、`batch-management`。
- **模块目录**：`specs/<module-slug>/`，固定含三文件：`spec.md`、`plan.md`、`tasks.md`。
- **文档文首字段**：模块、版本（`v1.0`）、日期（`YYYY-MM-DD`）、状态、依赖。
- **常量/标准引用**：合规约束统一称 `C1..C6`（定义于 `specs/constitution.md` 第 6 节）；示例产线/企业信息可用「清禾生物 · 一车间 / 柠檬酸发酵」作占位。

## 4. 章节强制顺序

- `spec.md`：概述 → 用户场景 → 功能需求(EARS) → 非功能需求 → 边界与约束 → 成功标准 → 现状对照。
- `plan.md`：架构概览 → 数据模型 → 关键技术决策 → 集成点 → 合规与安全设计 → 风险。
- `tasks.md`：任务（带目标+验收） → 进度总览。

## 5. 现状对照表约定

每个 spec 末的「现状对照」用两列标记：

| 标记 | 含义 |
| --- | --- |
| ✅ | 原型已实现，文档固化现状 |
| ❌ | 原型缺失，属工业级缺口，需在 tasks 中排期 |

## 6. 合规引用

质量/审计/RBAC/追溯等判定必须回指 `constitution.md` 的 C1–C6，不在单模块内重新定义合规口径。`plan.md` 的「合规与安全设计」须逐条说明如何满足相关 C 约束。

## 7. 版本与变更

- 文档版本格式 `v<主>.<次>`，重大结构调整升主版本。
- 文首记录 `版本 · 日期`；章程（constitution）修改须评审留痕。
